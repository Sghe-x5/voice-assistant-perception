# Кодбук 0.2: эпизод, ход и вопрос о параметре

Статус: рабочая схема и проверки реализованы; надёжность на человеческом корпусе
ещё не установлена. Связь: `field-diary-1.1` → `fieldwork.prepare` →
`field-coding-1.1` → `fieldwork.compare`. Кодбук разделяет сказанное пользователем,
вход, доступный ассистенту, и наблюдаемую форму вопроса. Наличие текста во входе
не доказывает понимание или запоминание внутри модели.

## Единицы и поля эпизода

Эпизод — одна цель до завершения, смены цели или отказа. Сохраняются participant,
session и episode IDs: несколько ходов не становятся независимыми людьми.
Пять прежних полей описывают эпизод в целом и остаются в формате:

| Поле | Допустимые значения |
|---|---|
| task_family (список) | fact, state_action, constrained_planning, explanation, creative, social, mixed, unknown |
| information_state (список) | sufficient, missing_parameter, ambiguous_reference, conflicting_constraints, unknown |
| assistant_action (список) | answer, act, targeted_question, broad_repeat, explicit_assumption, acknowledge_error, revise, refuse, other, unknown |
| repair_outcome | resolved, partial, unresolved, abandoned, not_applicable, unknown |
| objective_result | success, partial, failure, unscorable, unknown |

`information_state` — обзор эпизода, НЕ состояние перед каждым вопросом. Для
исследования повторных запросов используются только структурированные вопросы
ниже. `evidence_reference` указывает конкретное основание эпизодной разметки.
Не размечено = `null`; рассмотрено, но неизвестно = `unknown` или `["unknown"]`.
Нельзя смешивать unknown и определённые значения в одном списке.

Входные метаданные: `sampling_role` (`developer_pilot` / `volunteer`),
`evidence_origin` (`human_assistant_recorded` / `human_human_recorded` /
`retrospective_report`), modality, recorded_at, product/version, goal, context,
account и отдельный человеческий smartness 1–7/null. `account` не заменяет
структуру ходов. `recorded_at` — время записи дневника, не latency.

Дополнительные поля версии 1.1:

- `turn_coverage`: complete / partial / unknown. Порядок массива `turns` —
  хронологический порядок, а не лексикографическая сортировка ID.
- `coding_partition`: development / held_out / unassigned. Авторские эпизоды
  не принимаются как held_out. Назначение раздела фиксируют до независимой разметки.
- `turns`: последовательность ходов, описанная ниже.
- `question_units`: заранее зафиксированный список кандидатов «ход × параметр».

## Ходы: два канала доказательств

Каждый ход содержит ровно `turn_id`, `speaker` (user / assistant / tool), `text`,
`evidence_reference`, `assistant_context_before`.

`text` — речь/текст в источнике, а НЕ автоматически распознанный вход модели.
У user/tool `assistant_context_before` равен null. У assistant он тоже null,
если фактический вход неизвестен. При наличии записи входа:

```json
{
  "text": "Текст входа, реально предоставленного ассистенту до этого хода",
  "source": "request_log",
  "complete": true,
  "evidence_reference": "Локальный журнал, request 17, до ответа T4"
}
```

Разрешённые source: `request_log` или `controlled_script` для инструментированного
контролируемого взаимодействия. `complete` относится ко всему заявленному
контексту этого запроса. Частичный фрагмент нельзя выдавать за полный вход.
Пустая строка возможна только как реально наблюдавшийся пустой вход.
При невозможности установить вход — null; пересказ или текст произнесённой речи
не копировать туда как будто это журнал модели.

В коммерческом голосовом приложении полного входа часто нет. Это ограничение
данных: состояние ассистента будет unknown. Ни транскрипт речи, ни видимая история
сами по себе не подтверждают отсутствие ASR-ошибки, обрезки истории или скрытого
контекста. Для механистического эксперимента нужен контролируемый интерфейс.

## Кандидаты вопросов

Координатор до разметки фиксирует кандидатов по всему доступному эпизоду:

```json
{"turn_id":"T4","parameter_id":"duration","parameter_definition":"Длительность таймера, требуемая задачей"}
```

Ход должен быть assistant, пара turn_id/parameter_id уникальна. Несколько
параметров в одном вопросе — несколько единиц. Parameter IDs и определения общие
для обоих разметчиков. Сначала отдельно проверяется полнота этой инвентаризации;
согласие на фиксированных единицах не оценивает качество поиска самих вопросов.
Если найден пропущенный кандидат, создаются два новых пакета и оба размечаются
заново; нельзя добавить строку только одному разметчику.

## Разметка конкретного вопроса

Каждая автоматически созданная строка `questions` содержит:

| Поле | Правило |
|---|---|
| turn_id / parameter_id | Не изменять; задают общую единицу |
| is_question | true / false / null; false сохраняет спор о наличии вопроса |
| user_information_before | supplied / not_supplied / conflicting / unknown / null |
| user_evidence | Список {turn_id, quote}; только предшествующие user-ходы и точные фрагменты |
| assistant_information_before | available / absent / conflicting / unknown / null |
| assistant_evidence | Точные фрагменты из assistant_context_before этого хода |
| request_kind | new_information_request / repeat_known_information / confirmation / other / unknown / null |
| candidate_value | Для confirmation: значение, явно произнесённое в вопросе; иначе null |
| coding_note | Объяснить связь вопроса, параметра, источника и оценки |

Правила:

1. `new_information_request`: параметр отсутствует в подтверждённом полном входе
   ассистента. Это не обязательно новый параметр для пользователя.
2. `repeat_known_information`: значение доступно во входе; ассистент заново
   запрашивает его без предъявления конкретного кандидата. «Known» здесь означает
   доказанную доступность, а не доказанное внутреннее знание модели.
   Значение должно быть применимым к определённому параметру: прежняя догадка
   ассистента, устаревшая инструкция или просто упомянутое число не доказывают
   предпочтение пользователя. Источник, область действия и спорные случаи
   объясняются в coding_note; код не может проверить этот смысл автоматически.
3. `confirmation`: вопрос предъявляет конкретное значение для проверки.
   Например, «Десять минут, верно?». Он может быть разумным при неопределённости;
   не кодировать его автоматически как память, сбой или бесполезное повторение.
4. «Можно выполнить это действие?» — разрешение на действие; для данного
   информационного параметра `other`, а не повтор значения. Не смешивать
   подтверждение значения и авторизацию действия.
5. `supplied/available` требуют положительного свидетельства;
   `conflicting` — не менее двух разных свидетельств, смысл конфликта проверяет
   человек. Код проверяет ссылки и фрагменты, но не понимает их содержание.
6. `not_supplied` допустимо только при полном покрытии пользовательских ходов;
   `absent` — только при полном входном снимке. Неизвестность не равна отсутствию.
7. Если is_question=false/null, зависимые метки остаются null. Кандидаты не
   удаляются: пропуск нельзя скрыть уменьшением знаменателя согласия.

## Пример изменения состояния (полностью придуманный, только для объяснения)

| Ход | Наблюдение | Корректная трактовка |
|---|---|---|
| T1 user | Произнесено «на десять минут» | Пользователь сообщил значение |
| T2 assistant | «На сколько?»; в записанном входе только «таймер» | user=supplied, assistant=absent, new_information_request. Возможно ASR-потеря, а не забывание |
| T3 user | «Десять минут» | Новое свидетельство |
| T4 assistant | «На сколько?»; теперь вход содержит десять минут | assistant=available, repeat_known_information |
| T6 assistant | «Десять минут, верно?» | confirmation; candidate_value — точный фрагмент вопроса |

При отсутствии журнала входа T2 нельзя объявлять ни повторным запросом известного,
ни доказанной ASR-потерей. Он получает assistant=unknown, request_kind=unknown;
форма подтверждения иногда устанавливается по самому вопросу независимо от входа.

## Независимость, версии и отчёт

В каждой эпизодной строке разметчик указывает `episode_familiarity`:
`own_episode`, `seen_before`, `new_to_coder`, `unknown` или null. Скрытие рейтинга
и бренда не стирает память автора о своём разговоре. Координатор, готовивший
текст, также мог его видеть. Отчёт разделяет знакомые обоим/одному и заявленно
новые обоим материалы; это самоотчёт, не гарантия ослепления.

Сначала авторские developer pilot эпизоды для отладки. Затем внешние добровольцы;
кодбук уточняется на development части. После фиксации версии — новые внешние
эпизоды в held_out, не использованные для обучения разметчиков/изменения правил.
После изменения правил нужна новая проверочная часть. Сохранять первоначальные
метки до согласования. Ни роли авторов, ни повторные ходы не увеличивают N людей.

Версия 1.0 дневника продолжает читаться, но получает `legacy_unavailable` и пустой
инвентарь вопросов; это означает отсутствие детальных данных, а не отсутствие
вопросов. Старые пары coding-1.0/кодбук-0.1 сравниваются как раньше. Нельзя смешивать
версии: для новых вопросов вручную реконструировать ходы по оригиналам, явно
перейти на diary-1.1 и подготовить/разметить оба пакета заново. Старые метки и
оригиналы сохраняются, автоматической миграции их смысла нет.

Отчёт даёт эпизодные и вопросные показатели отдельно: paired denominator,
missing/unknown, confusion, точное совпадение и nominal Cohen kappa. Отсутствует
доверительный интервал; зависимость вопросов внутри эпизода/человека не исчезает.
Метки repair_initiator/target и количественная нагрузка не входят в машинную
схему 0.2: не обещать их автоматический расчёт по свободному описанию.
